# a2a-arch-r06: what changed, the red-to-green tests, how to check each by hand

Spec: `.kiro/specs/a2a-arch-r06/bugfix.md`. Base: HEAD 7165162 (the second review round of the a2a-arch-r05 fixes). Each item has a red commit (`[kiro] a2a-arch-r06: red …`, the new tests failing for the reason named), then a fix commit (`[kiro] a2a-arch-r06: fix …`). `git log --oneline 7165162..` lists them in order. After each fix: `npm test`, `npm run typecheck`, `npx oxlint` and `npm run build` were run and were green; every a2a-arch-r05 test stayed green and none was edited.

Two process notes.
- The C2 and C6 red commits carry an API skeleton: `src/data/deadline.ts` (a `withDeadline` that never times out), the extra optional parameters of `createShelfLoader` and `loadNoteAssets`, and `src/cook/visibleTimer.ts` (a countdown on the wall clock). They exist so the red tests typecheck and fail on behaviour, not on a missing import. The skeleton is what the code did before the fix.
- The red runs were read for their failure messages, not counted: C1 "expected null not to be null" and "Cannot read properties of null (reading 'dispatchEvent')" (no button); C2 "no answer" tests timing out after 30 s (the unfixed code never settles); C3 "expected null not to be null" for `.static-pane`; C4 "expected vi.fn() to be called 3 times, but got 2 times"; C5 "expected 0 to be greater than 400" (the reveal clock stood still); C6 "expected '#/r/quinces-marmalade/quoted' not to be '#/r/quinces-marmalade/quoted'"; C7 "expected true to be false" for `hasAttribute('aria-hidden')`.

## Tests changed on purpose

- `src/data/catalog.test.ts`, table test "a network error leaves the recipe out …": its `toEqual` now also expects `transient: true` for the network-error row only (C1). The other rows still expect no `transient` key.
- `src/data/catalog.test.ts`, "a load that still fails after the retries is reported, warned once, and not cached" (a2a-arch-r05 B5): the expected rejection gains `transient: true` (C1). The scenario and every other assertion are unchanged.
- `src/data/catalog.test.ts`, "caches: one fetch per id" (R2.7): `toHaveBeenCalledWith(url)` became `toHaveBeenCalledWith(url, { signal: expect.any(AbortSignal) })`, because the request now carries the deadline's signal (C2).
- `e2e/steam-look3.spec.ts`, "the reviewed reading shows under the pane …": `aria-hidden="true"` on `[data-note-reading]` became "no `aria-hidden`, no `aria-hidden` ancestor", plus "the canvas stays `aria-hidden`" (C7). It encoded the defect.

No r05 test file was edited.

Check the connection.") and a "Try again" `button.btn` (48 px high from `.btn`, a native button, `aria-disabled` while a run is in flight). The retry prop is given only for a route id that has a transient rejection. Copy is in `src/copy/strings.ts`. A retry that fails again announces the line again.
- Red to green: `src/app/App.test.tsx`, describe "a deep link whose load failed on transport can be retried (a2a-arch-r06 C1)": "a transient rejection shows the one short line and a "Try again" button …", "Try again runs the loader again; a recipe that loads replaces the not-found screen on the same route", "a retry that fails again keeps the screen and the button, usable again", "the window "online" event runs the loader again …", "the button is keyboard operable …", "a retry already running is not started twice". `src/data/catalog.test.ts`, describe "a rejection that ended on transport is marked (a2a-arch-r06 C1)". Passing before and after: "a 404 or a content failure keeps the plain not-found: no line, no button, and "online" does nothing", "an id the catalog does not list is plain not-found …", "the button is at least 44 px high in app.css".
- e2e (real browser, service worker blocked so `page.route` sees the request): `e2e/shelf-retry.spec.ts`, 3 tests, passed: 503 for the first requests then "Try again" by keyboard (Enter) loads the recipe on the same hash; `online` loads it with no click; a 404 shows no line and no button.
- By hand: open `#/r/quinces-marmalade` with DevTools, Network, "Offline" ticked. After about 1.3 s the page says "This recipe is not on the shelf" and "The recipe did not load. Check the connection." Untick Offline: the recipe opens by itself (online event). Or tick it again, reload, untick and press "Try again".

## C2. A request that hangs ends

- Changed: new `src/data/deadline.ts`: `withDeadline(ms, run(signal), { signal?, timers? })` races `run` against a timer, aborts its signal at the deadline, clears the timer on any settle, rejects `DeadlineError` ("no answer within N s"), and re-throws the caller's own abort as an abort (an already aborted signal never starts `run`). Constants `RECIPE_DEADLINE_MS` 10 000, `NOTE_DEADLINE_MS` 15 000, `PANE_JSON_DEADLINE_MS` 10 000. `src/data/catalog.ts`: the request and the body of `recipe.json` share one 10 s deadline; a timeout is a transport failure, so a2a-arch-r05 B5 retries it (`createShelfLoader`'s 4th parameter is the timers). `src/steam/assets.ts`: `fetchOk` became `fetchRead`, which covers the body too; a timeout is an `AssetError` for the field (`meta`, `note`, `toi`) with "no answer within 15 s"; a caller abort is re-thrown as it is (`loadNoteAssets`'s 4th parameter carries the timers). `src/steam/SteamPane.tsx`: its `<stem>.json` fetch has a 10 s deadline and an `AbortController` aborted on unmount; a timeout lands in the existing `.catch`. `src/data/timers.fixture.ts`: hand-driven timers for the tests.
- Assumption: `SteamPane` has no error state of its own for that JSON (its `.catch(() => {})` leaves the text empty; the glass has its own `error` status for the assets). "Its existing error state" is read as that `.catch`. Nothing was added to the page.
- A body that fails after a successful header (`res.blob()`) is now reported as "could not fetch <url>", where it used to be "could not decode <url>". The decode of a fetched blob still says "could not decode".
- Red to green: `src/data/deadline.test.ts` (8 tests), `src/data/catalog.test.ts` describe "a recipe request that hangs (a2a-arch-r06 C2)" (abort after 10 s and not before, the B5 waits 300 and 1000 ms, three attempts then a transient rejection; a body that never arrives; a hung load is not cached; an answer in time leaves no timer), `src/steam/assets.test.ts` describe "loadNoteAssets deadlines (a2a-arch-r06 C2)" (field `note` at 15 s and not at 14.999 s, field `meta` for the JSON and for its body, a caller abort stays `AbortError`, a rejection that is not a timeout keeps "could not fetch"), `src/steam/SteamPane.test.tsx` describe "SteamPane note JSON deadline (a2a-arch-r06 C2)" (abort at 10 s, none before; unmount leaves no timer).
- By hand: DevTools, Network, add a request-blocking rule that stalls (Chrome: throttle to "Offline" does not hang; use a local proxy that accepts and never answers) for `/recipes/quinces-marmalade/note-*.png`: in Cook Mode, after 15 s the typed transcription shows in place of the scan (R15.12). Not run by hand here: I had no stalling proxy, the claim rests on the unit tests with injected timers.

## C3. A note that went static stays static

- Changed: `src/steam/SteamGlass.tsx`: `useStatic = wantsStatic || stuckStatic`, where `stuckStatic` is set during render the first time the static pane is wanted (reduced motion, no WebGL2, lost context, tier 3). The live effect is keyed on `status`, so it never builds a second, fogged renderer for a revealed note. The next note is a new mount (`PaneStage` keys the glass per note), so it may be live again.
- Decision: the latch holds for any reason, including a page that was reduced from the start. A reduced-motion page whose reveal was already started on the static pane would otherwise have the same fault, and the glass cannot tell a started reveal from a fogged one (the static pane reports `fogged` too). Cost: reduced motion switched off before a note was ever revealed leaves that one note static.
- Red to green (`src/steam/SteamGlass.resume.test.tsx`, describe "once static, a note stays static (a2a-arch-r06 C3)"): "reduced motion switched off again while the note is held: the pane stays static, held, and the wipe still works", "the next note's pane (a new mount) is live again once reduced motion is off". Passing before and after: "tier 3 then reduced motion on and off …", "a page that is reduced from the start and stays so is unchanged …"; the four a2a-arch-r05 B4 tests too.
- By hand: Cook Mode at a held note, DevTools, Rendering, "Emulate prefers-reduced-motion: reduce", then back to "no preference": the note stays on the glass and the Wipe control still wipes. Step to the next note: its pane is the live canvas.

## C4. A gesture asks again for an idle wake lock

- Changed: `src/cook/wakelock.ts`: `onGesture()` asks when the status is not `held`, nothing is pending and the lock was not released by us (`released` is set by `release()` and cleared by the next `acquire()`). It resets the one-time automatic re-acquire, so a lock the browser keeps taking away costs at most one request per gesture and one automatic one.
- Red to green (`src/cook/wakelock.test.ts`, describe "a gesture asks again for a lock that is idle (a2a-arch-r06 C4)"): "the next gesture asks again, and the lock is held", "the automatic re-acquire is spent again by that gesture …" (no loop), "a gesture refused again leaves it refused …", "a gesture while the lock is held asks nothing", "a gesture while a request is in flight does not start a second one". `src/app/Cook.wake.test.tsx`: "after the browser has released the lock twice, the next pointerdown in Cook Mode asks again and data-wake is held". Passing before and after: "a gesture after release() (Cook Mode closed) asks nothing", "a gesture asks nothing without the API", every a2a-arch-r05 B7 test.
- By hand: not reproducible on demand (it needs a browser that releases the sentinel twice, for example battery saver switching on and off). The Cook test fakes exactly that order.

## C5. The renderer clock resumes without `visibilitychange`

- Changed: `src/steam/renderer.ts`: `resumeIfVisible()` applies `handleVisibility()` when `hiddenAt` is set and the visibility source says the page is not hidden. It runs at the start of `frame()` and inside `clockNow()` (so `startReveal()` and `wipe()` are covered).
- Red to green (`src/steam/renderer.test.ts`, describe "SteamRenderer clock when visibility comes back without an event (a2a-arch-r06 C5)"): "the next frame advances the write-on, and the gap is not a frame", "a wipe asked for after a silent restore sweeps instead of standing still", "startReveal after a silent restore starts a reveal that runs, from the visible time". Passing before and after: "a page that is still hidden stays frozen, and the real event afterwards still resumes it once" (the gap is shifted once, not twice); the five a2a-arch-r05 B1 tests.
- By hand: not reproducible on demand (needs a restore from the back-forward cache that skips the event). In DevTools you can see the fixed path: in the console, run `Object.defineProperty(document, 'visibilityState', { value: 'hidden', configurable: true }); document.dispatchEvent(new Event('visibilitychange'))`, wait, then `Object.defineProperty(document, 'visibilityState', { value: 'visible', configurable: true })` with no event: the glass carries on.

## C6. The hand-over waits for the sweep

- Changed: new `src/cook/visibleTimer.ts`: `createVisibleTimer(ms, fn, env?)` counts only visible time. It pauses on hidden, resumes on `visibilitychange`, `pageshow` and `focus` when the page is visible, fires once, and `cancel()` is idempotent. A timer that fires while the page is hidden (a hide it never saw) waits for the page. `src/app/Cook.tsx`: the final hand-over uses it with `WIPE_MS`; `timers.current` now holds cancel functions and the unmount cleanup calls them. Chosen over "follow the pane reporting the sweep finished": the pane's report differs between the live canvas and the static pane, and the countdown is testable with injected time. Visible behaviour is the same 1400 ms.
- Red to green: `src/cook/visibleTimer.test.ts` (8 tests: full time while visible; stands still while hidden and fires after the rest; adds up over several hides; starts hidden; pageshow or focus without `visibilitychange`; cancel; leaves nothing behind; a hide it never saw). `src/app/Cook.test.tsx`, describe "the hand-over after the last wipe waits for visible time (a2a-arch-r06 C6)": "hiding the phone within the sweep keeps the sweep …", "a pageshow with no visibilitychange resumes the countdown when the page is visible". Passing before and after: "visible behaviour is unchanged: not before 1400 ms, there by 1500 ms", "closing Cook Mode during the sweep cancels the hand-over".
- By hand: open the hero deep link, wait for the hold, press Wipe on the last step and switch tabs within a second. Come back: the sweep finishes, then "The hand, quoted" opens.
